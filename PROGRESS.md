# Progress Notes

Running log of milestones, decisions, and fixes for the drone soccer striker
task. Chronological within each section; newest at the bottom.

## Naming convention

`vX.Y[.zip]` — `X` is the lineage, `Y` is the stage within it. A fresh start
(`train.py`) begins a new `X.0`; a continuation (`train_continue.py`) bumps
`Y` on the same lineage. `X` changes only when core physics changes (so far:
`ATTITUDE_GAIN`), not for reward-shaping/hyperparameter tweaks — those stay
within a lineage as stage bumps. `_regressed` marks a stage's raw final save
when that stage's own best checkpoint (no suffix) is a different, earlier
file — see the PPO non-monotonic-regression finding below for why both
sometimes exist. `_abandoned` marks a lineage or stage that was cut off
without reaching a real conclusion.

Renamed from the original ad hoc `v1, v2, v3, v4, v5, v6/v6_best,
v7/v7_best, v8` scheme (and tensorboard's `Baseline`/`Stage_1-6`) partway
through — the table below uses the new names throughout; where useful, a
note calls out what a model or run used to be called, since commit history
and any old screenshots/reports still use the old names.

## Key findings & fixes

- **Flip/miss had no reward penalty.** `_check_done()` could end an episode as `"flipped"` or `"missed_goal"`, but `_compute_reward()` had no matching branch — those outcomes scored the same as an ordinary step, so the policy had no direct incentive to avoid them beyond losing future progress reward. Added `FLIP_PENALTY=-30`, `MISS_PENALTY=-10`.
- **`ent_coef=0.01` caused an entropy runaway once those penalties were added.** Continuing `v1.0`→`v1.1` with the old ent_coef, action `std` climbed monotonically from ~1.4 to ~5.5 over 4M steps (never plateaued) — the entropy bonus outweighed the policy-gradient signal while the value function was still adjusting to the new reward scale. With actions clipped to `[-1, 1]`, that std means most sampled actions are just noise slammed against the clip boundary. Fixed by lowering to `ent_coef=0.001`; re-ran `v1.0`→`v1.1` clean (std settled to ~0.7).
- **`out_of_bounds` has the same missing-penalty gap** as flip/miss did — not yet fixed, and crept up to 6% in `v1.1`'s final stretch. Candidate follow-up.
- **Flip mechanics diagnostic** (60 headless episodes against `v1.1`): even non-flip episodes reach ~80° tilt on average (task requires very aggressive flight near the tilt limit as normal operation, not just in failure cases). In the last 15 steps before an actual flip, angular velocity *accelerates* (7.5 → 14 rad/s) while action magnitude stays high/near-saturated the whole time — the policy is actively fighting the spin, not ignoring it; available roll/pitch torque authority (`ATTITUDE_GAIN=0.4`) just isn't enough to arrest it once started. Suggests raising `ATTITUDE_GAIN` or `angularDamping` as a control-side fix, separate from reward tuning. **Not yet implemented** at the time — deprioritized after the large-sample data below showed missing, not flipping, is the bigger failure mode. (Later tried in the `v1.5_abandoned`/`v2.0` work above — see Open items for the result.)
- **Large-sample check (3125 episodes) showed `missed_goal` (52%) is the dominant failure mode, not `flipped` (37%)** — the 60-episode diagnostic above was noisy on this point. Root cause: `PROGRESS_SCALE` shapes toward raw 3D distance to `goal_pos`, which doesn't specifically reward staying centered on the hoop's Y-Z opening — a drone can reduce net distance while drifting off-axis and only find out at the goal plane.
- **Final-approach lateral shaping added** to address the above: `LATERAL_SCALE=10.0` potential-based reward for reducing Y-Z distance to the hoop center, gated to `drone_pos[0] >= FINAL_APPROACH_X (2.0)` so it doesn't fight goalkeeper-dodging earlier in the flight. Result (`v1.1`→`v1.2`, 4M steps): worked, but not obviously so from the raw `missed_goal` % alone (52%→56%, looks flat/worse) — the useful read is conditional shot accuracy, `scored/(scored+missed_goal)`, which roughly doubled (~8.3%→~17.1%). Raw `missed_goal`% rose because `flipped`/`out_of_bounds`/`crashed` all dropped, funneling more episodes into "reached the goal plane" at all, and only part of that larger pool converts to scores yet. Lesson: don't read `missed_goal`% in isolation when other failure modes are shifting at the same time.
- **Checkpoint/tensorboard naming collisions**, twice: `train_continue.py`'s `CheckpointCallback` name_prefix and `tb_log_name` need to be unique per lineage — `reset_num_timesteps=False` makes SB3 reuse the *latest existing* run directory for a given name rather than incrementing, so reusing a name across different training lineages silently interleaves unrelated runs' curves or overwrites old checkpoint files at the same step numbers.
- **PPO's non-monotonic regression hit `v1.3`/`v1.4`'s stages, but not `v1.1`/`v1.2`'s.** Checked every stage's final save against its own `EvalCallback`-picked best checkpoint with a matched 150-episode eval: `v1.1` and `v1.2`'s final saves were fine (tied or better than their "best" pick — the callback's noisy 10-episode checks aren't always right either). The stages that produced `v1.3`/`v1.4` had genuinely regressed by their final save (more than 2x worse scoring than their mid-run peaks — those raw final saves are `v1.3_regressed`/`v1.4_regressed`). Lesson: this has to be checked per-run, not assumed either way — neither "the final save is always right" nor "always distrust the final save" holds. **`v1.4` is the best model in the `ATTITUDE_GAIN=0.4` lineage.**
- **Cross-lineage eval bug: `ATTITUDE_GAIN` (and any other module-level env constant) isn't saved inside a model checkpoint, so evaluating an older model against the *current* `drone_soccer_env.py` silently evaluates it under physics it never trained for.** First automated comparison of `v1.5_abandoned` vs `v1.4` (after that stage changed `ATTITUDE_GAIN` 0.4→0.6) scored `v1.4` at only 6.7% — re-evaluating it under its native 0.4 got 26.7%, matching its previously-documented 27.3%. The 6.7% figure was pure artifact of evaluating a 0.4-trained policy under 0.6 physics, not a real result. Any future comparison across a lineage that changed such a constant needs each model evaluated under *its own* training-time value, not both forced through whatever the file currently says. `eval_model.py` doesn't guard against this automatically — mitigate by temporarily setting the constant back before evaluating the older model, as done here, until/unless the constant is made a parameter instead.
- **`RANDOM_OPPONENT_SPEED` units bug — found live by the user watching `v2.4` behave erratically.** The constant is metres moved per env step (one physics tick, 1/240s), not metres per second, so `0.02` (a wander-mode value, fine for slowly cruising toward a distant waypoint) was actually **4.8 m/s** once chase mode made it a continuous pursuit — fast enough to cross the whole 2.09m field in under half a second, every tick. The original bundled `v3.0` attempt had explicitly calibrated this to `0.005` (1.2 m/s, "capped below the striker's own top speed so it's genuinely evadable"), but that calibration got silently swept away by the "revert everything to `v2.2` except chase mode" fix, which didn't recognize this constant needed separate treatment for chase vs. wander, the same way `CHASE_STANDOFF_RADIUS` did. **Both `v2.3` and `v2.4` were trained under the broken 4.8 m/s speed** — discarded rather than kept as reference. Fixed: renamed to `RANDOM_OPPONENT_SPEED_MPS=1.2`, converted via `/PHYSICS_HZ` at module load, so the constant's units can't silently drift again.
- **Spherical drone-soccer cage body tried, then reverted.** Built `assets/tello_cage.urdf` (20cm sphere, `cf2x.urdf`'s rotor mounts copied over verbatim, closed-form spherical-shell inertia tensor) to replace `cf2x.urdf`'s rotor-frame shape. Physically sound (sanity-checked rotor offsets/mass/inertia/collision shape directly) and genuinely different dynamics — ~8-13x more rotational inertia than the old cf2x-scaled tensor, making the drone far more flip-resistant but more sluggish to maneuver, confirmed via a 40-episode random-action check (zero `flipped`, vs. `v1.0`'s 82.8% baseline). Diagnostic fine-tune from `v2.2` (short, 2M-step budget) flatlined at 0-1% scored for 1.75M steps with no trend — same failure shape as `v1.5_abandoned`'s `ATTITUDE_GAIN` mismatch, a physics change too large to fine-tune through. **Reverted to the normal `cf2x.urdf` body** before any full training commitment, per user direction — the cage is shelved, not abandoned as an idea, just not pursued further this lineage.
- **Reverting to the normal body broke the detector, which led to finding and fixing several real bugs.** The cf2x frame's real silhouette (~8cm, its rotor arm span) is far smaller than the cage's 20cm diameter, so the same auto-labeling approach produced boxes only ~2.5px wide at the original `img_size=84` — below what YOLO's finest detection grid can resolve (confirmed: mAP50 collapsed from the cage's 0.995 to ~0.02, barely above chance). Fixed with two changes: (1) `img_size` 84→160 (more pixels per object), funded by (2) decoupling detector calls from `PHYSICS_HZ` (240Hz) to a realistic `DETECTOR_HZ=30` matching real Tello video — camera/detector now only actually runs every `DETECTOR_STEP_INTERVAL` (8) steps, reusing the last detection in between, which also cut render+inference cost ~8x. Retrained (mAP50 0.90, precision 0.90, recall 0.80) — far more usable, though not the cage's near-perfect numbers, since it's a genuinely harder target (smaller, lower-contrast grey-on-grey). `DRONE_CAGE_RADIUS`-dependent labeling math in `generate_detector_dataset.py` replaced with `DRONE_BOUNDING_RADIUS=0.04` (cf2x's own arm length) as a non-spherical-body labeling approximation.
- **`YoloDetector` was silently using the GPU for in-loop RL inference, serializing all `N_ENVS` parallel workers on one device.** Caught live by the user noticing Task Manager showing GPU usage and most CPU cores idle instead of parallel load — `ultralytics` auto-selects CUDA when available and no `device=` was ever passed, so all 12-14 subprocess workers queued for the same GPU context instead of doing independent CPU work, each one blocked waiting its turn rather than computing in parallel. Fixed: `YoloDetector` now defaults to `device="cpu"`. `train_detector.py`'s one-time detector *training* correctly stays on GPU (`device=0`) — no multi-process contention there, just one process, and training itself got ~3.3x faster on GPU (50 epochs in 5.2min vs ~17-20min on CPU) on top of the accuracy fix above.
- **Defender-standoff bug: the chasing defender could fully overlap the striker, not just touch it, trapping episodes until `max_steps`.** Caught live by the user watching `v4.0` fly — "the opponent drone gets too close, it clipped together, causing the max step because the drone can't really go anywhere." Root cause: the defender is kinematic (`resetBasePositionAndOrientation` every step, not pushed by real physics), and its chase target was literally `drone_pos` with zero offset — once within `OPPONENT_SPEED` of the striker it snapped to the *exact same coordinates* and kept re-snapping there every subsequent step, no matter how the striker moved, since there was nothing to physically push it away. A standoff offset existed for the old multi-opponent chase mode (`CHASE_STANDOFF_RADIUS`) specifically to stop chasers stacking on *each other*, but was dropped entirely (not just resized) when simplifying to a single defender — missing that it was also preventing overlap with the striker itself, a different problem with the same fix. Added `DEFENDER_STANDOFF_RADIUS=0.15`: the chase target is now `drone_pos` offset back along the approach vector by that distance, verified directly (forced close-proximity test over 2000 steps never closed below 0.1500). `v4.0` trained under the buggy version the whole time — likely explains its volatile 2M-step tail (oscillating 9%-70% scored) and its deeply negative `ep_rew_mean` despite decent scoring (a trapped episode racks up `COLLISION_PENALTY` every step for up to 1000 steps). Re-evaluating `v4.0`'s own checkpoint under the fix dropped it to 57.3% (from 67.3% under the bug) — within plausible eval-to-eval noise (`deterministic=False`, same reset seeds but not action-sampling seeds, ~±4pt standard error at n=150), not confidently attributable to the fix itself. Fine-tuning through the fix (`v4.1`, +2M steps) worked cleanly — 80.7% scored, the project's second-best result — confirming this was a bug fix the policy adapts to easily, not a difficulty change needing a fresh start.
- **The `DEFENDER_STANDOFF_RADIUS=0.15` fix above overcorrected — found live by the user watching `v4.1` fly, "sometimes the defender drone just stop before it hits the striker drone, this should not happen, if it hits, it should collide."** 0.15m is larger than the two `cf2x` collision cylinders' actual contact distance (~0.12m), so the fixed standoff prevented genuine collision entirely rather than just the full-overlap case — the defender hovered just outside contact range, never close enough to trigger `COLLISION_PENALTY` or real contact physics. Replaced the fixed-distance standoff with a contact-aware one: the defender now closes the *entire* distance to the striker (no offset) unless `_collided_with_opponent()` reports actual contact that step, in which case it holds its current position instead of continuing to advance — lets genuine collision happen (verified: minimum distance 0.0832m, real contact registered via `getContactPoints`) without re-introducing the original exact-coincidence freeze. `DEFENDER_STANDOFF_RADIUS` removed. **Re-evaluating `v4.1` (trained entirely under the no-contact-buffer version) zero-shot under this corrected physics jumped to 89.3% scored, 90.5% shot accuracy** — up, not down, despite never training on real collision — plausibly because genuine contact + restitution gives an actual physical bounce separating the two drones, which the old buffer-hover (persistent close proximity, no separating force) didn't provide. **New best result overall under the detector-based lineage.**

## Hardware / throughput notes

- Training is CPU-bound (PyBullet physics stepped across `SubprocVecEnv` workers), not GPU-bound — the policy net (tiny MLP+LSTM) barely uses the GPU (~13% util observed).
- Current machine: Ryzen 5 7500F (6 cores/12 threads). `N_ENVS` raised from 8 → 10 (oversubscribing SMT threads, leaving 2 free for main process/OS) — safe and effective in practice.
- If moving to a Ryzen 7 9700X (8 cores/16 threads): recommend `N_ENVS≈13-14` (same oversubscription ratio), not just matching physical core count. Estimated ~5-5.5h for a run that takes 8h here (more parallel envs + faster per-core Zen5 performance).
- **Task Manager showing only ~36% CPU utilization during training led to a deeper look.** Initial hypothesis (SubprocVecEnv's Windows IPC overhead dominating) was wrong: a side-by-side benchmark of `DummyVecEnv` vs `SubprocVecEnv` inside the real training loop showed no difference (1.05x) — both settle to the same ~120-140 fps. The actual bottleneck is the **PPO update phase** (10 epochs x ~20 minibatches per rollout, LSTM forward+backward through each), not environment stepping — during that phase only the main process works while all env-worker processes idle, which is what shows up as low utilization. Confirmed fix: **`device="cpu"` beats the default `"auto"`/cuda by 1.29x** (130.6 vs 101.4 fps) for this tiny policy — GPU kernel-launch/PCIe-transfer overhead per minibatch exceeds the compute it saves. Applied to `train.py`/`train_continue.py`. Lesson: a raw single-env stepping benchmark without policy inference/gradient updates is not representative of real training throughput — measure the actual loop.
- **`tb_logs/` cleaned up and relabeled twice now**: first to `Baseline`/`Stage_1-4` matching an earlier report, then again to the current `vX.Y` scheme (see Naming convention above) — `Baseline`→`v1.0`, `Stage_1`→`v1.1`, `Stage_2`→`v1.2`, `Stage_3`→`v1.3`, `Stage_4_0`→`v1.4`, `Stage_5_0`→`v1.5_abandoned`. `Stage_6_0` (a few seconds of an immediately-cancelled run) was deleted rather than renamed. If continuing training on any lineage, keep using the `vX.Y` naming for any new tensorboard runs.
- **`RecurrentPPO_7` (`v1.0`'s own fresh-start training curve) was deleted too broadly in an earlier cleanup, then recovered from git history** — commit `9d16388` ("add more complexity to the env") had committed it before deletion, since PID `11892` in its filename matched the known `train.py` process that produced `v1.0`. Restored as `tb_logs/v1.0` (245 points, steps 4,096-1,003,520, matches `v1.0`'s known training window exactly). Earlier prototyping runs and the old `v0.1`→`v0.2` curve were *not* recoverable this way — they were never committed, so if needed again they'd have to come from OneDrive's cloud recycle bin (this whole project lives inside a OneDrive-synced folder) rather than git.

Lesson worth keeping: a policy fine-tuned under one physics setting can get stuck badly enough that a fresh start outperforms it even at a fraction of the total step count, and bundling several real-world-grounding fixes into one fresh lineage (rather than isolating each) was fine here since none of them were competing hypotheses.
- `out_of_bounds` penalty gap is now fixed (`OUT_OF_BOUNDS_PENALTY=-20`, no longer terminal — see the field/naming rewrite above).
- **`v2.2` (90.0% scored, 100% shot accuracy) is the best model overall**, by a wide margin over `v1.4`'s previous 27.3%/52.6%.
